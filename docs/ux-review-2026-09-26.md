# Kagi — implementation and demo UX review

Reviewed 26 September 2026 against `da9680a`. This is a review of the current implementation and a brief for the next design pass. No application, contract, firmware, wallet, or agent configuration was changed during this review.

## Assessment

The current architecture supports the intended story: a session key spends within an on-chain allowance; increasing that allowance needs the owner; adding a second stick strengthens approvals without changing the account address. The contract and local MCP tests pass. The biggest work before visual polish is reliable recovery and truthful status feedback.

The connected wallet was already **3 of 3**. I inspected its live Home, agent-key detail, new-key approval screen without granting, second-stick status, and navigation. Both attached sticks reported the joined configuration. I did not reset the wallet to repeat onboarding or initiate a fresh live spend, approval, reshare, or revoke.

## Current flow and semantics

1. The phone pairs with the Kagi Wallet and creates the wallet signing shares. The phone deploys/funds the on-chain account.
2. The phone creates an ephemeral session key with a **total lifetime allowance** and expiry. The owner unlocks the phone and holds A on the Kagi Wallet to grant it.
3. The key is handed to the MCP server. The existing app supports both a connector URL and a copied session-key bundle. For this demo, make the agreed **copy session key → paste into the agent** route the primary path.
4. The agent submits ETH transfers directly to the account. Under-cap transfers need no owner interaction. The agent pays its gas separately.
5. For an oversized transfer, MCP preflights the allowance and submits a limit request. This normal flow does not intentionally broadcast a reverting oversized payment. The contract independently enforces the cap, as exercised by the contract tests.
6. The phone reads the on-chain request. The owner approves a new total, with previous spending and expiry preserved. MCP observes confirmation and resumes the queued transfer.
7. Adding the second stick reshapes the same manager key into three shares. **Initial joining sends sealed pieces over BLE. Subsequent three-party approvals use IR between the sticks.** Depict these as distinct stages.
8. Once joined, grants and limit raises need phone + Kagi Wallet + second stick. Under-cap agent transfers still run independently. This is not a separate amount threshold that invokes the second stick only for large raises.

The implemented extension is specifically two signing parties becoming three. A closing message about other compatible devices should describe future protocol integration, not claim arbitrary device counts or automatic compatibility already implemented.

## Findings to address before design polish

These are source-level failure paths unless explicitly marked as observed in the live UI. Destructive failure cases were not exercised against the connected wallet.

### P1 — interrupted second-stick joining can strand the wallet

`mobile/src/app/vault.tsx:128–132` tells the Kagi Wallet to commit, waits for its acknowledgement, and only then persists the phone's new share. `firmware/wrist/src/main.cpp:1837–1848` replaces the Kagi Wallet's old share during that commit. A phone termination, failed acknowledgement, or failed phone storage write in this interval can leave the Kagi Wallet on three-party shares and the phone on its old share. The newly generated phone share existed only in memory, and retrying adoption is rejected once the Kagi Wallet is already three-party.

Persist a recoverable pending join before switching either side. Bind it to a join identifier and the target group/public shares; support idempotent commit, status queries, and recovery after restart. A generic error must not imply that nothing changed after one device has committed. Verify interruption before/after every commit and persistence boundary on disposable test state.

### P1 — firmware commit does not require a valid staged reshare

`firmware/wrist/src/main.cpp:1838–1841` checks only `rparties == 2` before copying `rX2new` into the live share. `rX2new` is a static buffer, and there is no guard here that a matching, physically approved reshare has populated it. A premature commit, or commit after a restart that lost the staged buffer, can replace the live share with an invalid value.

Require a durable, valid staged operation, its identifier, and the expected group/public-share data before committing. Reject premature, stale, and mismatched commits; return the recorded result for an already committed operation.

### P1 — revocation success can be displayed before on-chain revocation

`mobile/src/components/WristBridge.tsx:66–71` updates the old simulated store, starts real revocations without awaiting them, and opens `/revoke`. `mobile/src/app/revoke.tsx:13–25` immediately claims every key is dead on-chain. Meanwhile `mobile/src/lib/chainRevoke.ts:31–34` swallows offline/out-of-gas failures. Thus the strongest safety message can appear while the real session remains usable. Home's revoke action also has no useful pending or partial-failure result.

Show revocation progress based on real sessions and transaction receipts. Distinguish confirmed, pending, and failed keys, preserve transaction hashes, and provide retry. Announce completion only after the relevant receipts succeed.

### P1 — the legacy reset deletes the phone share before wrist confirmation

Home → More still opens `mobile/src/app/demo.tsx`. Its reset handler at lines 77–85 sends `wipe` and immediately deletes the phone shard. The Kagi Wallet asks for physical confirmation (`firmware/wrist/src/main.cpp:2023–2031`), but declining or disconnecting does not prevent the phone deletion. This route also does not implement coordinated cleanup of the newer root-share/session state or on-chain authorizations.

Remove this legacy reset from the presentation path. Any replacement needs explicit scope, device acknowledgement, and a coherent recovery/reset procedure. Do not use it to prepare the existing wallet for act one.

### P2 — pending transactions and queued payments are not recoverable enough

`agent-mcp/server.mjs:130–132` waits for a receipt before returning the transaction hash; at lines 202–204 a receipt timeout becomes a generic failure. A broadcast transaction may still confirm, so resending after that message can create another payment with a later nonce. The phone has the same ambiguity for limit raises (`mobile/src/lib/evm.ts:96–99`, `mobile/src/app/limit/[id].tsx:74–78`).

MCP also stores queued payments only in memory (line 214), reconstructs a request without its payment after restart (line 234), and clears the queued payment before sending it without caching the final result (lines 427–430). A lost response cannot be recovered by simply repeating the wait call.

Persist an operation identifier, payment intent, transaction hash, and result. Return “submitted / checking confirmation” separately from “reverted”; reconcile the original hash before offering a fresh send. Repeated waits should return the same payment result. Exercise restart and lost-response cases in addition to the passing happy path.

### P2 — concurrent BLE messages can interleave, and send failure is hidden

`mobile/src/lib/ble.ts:200–211` writes a message in awaited chunks but does not queue whole messages per device. A concurrent status/exposure/signing message can enter between chunks of a longer frame. `mobile/src/lib/link.ts:48–52` then returns success before the asynchronous write completes and discards a failed result. The user can be left waiting on a stick for a request that never arrived intact.

Serialize complete frames per device and propagate delivery failures into the pending operation. Verify concurrent long messages and disconnect mid-write. This is a source-level concurrency risk, not a reproduced radio failure in this review.

### P2 — the phone authentication gate can fail open

`mobile/src/lib/biometrics.ts:27–29` treats absent enrollment as success, and lines 40–42 also return success after native exceptions, even without `EXPO_PUBLIC_AUTOTEST`. Approval UI can therefore claim an unlock stage without actually verifying the owner. The stored shard reads do not independently require authentication.

Use a supported passcode fallback or an explicit verification error in the normal build. Keep bypass behavior confined to a visibly marked test build. Test cancellation, no enrollment, native errors, and successful authentication separately.

## Two-act rehearsal script

Use a dedicated wallet prepared in two-party mode for a fresh rehearsal. The currently connected wallet is already three-party; unplugging the second stick does not turn it back into two-party mode. Keep both sticks ready and adequately charged, and prepare the session key before the presentation.

Use a funded account with at least 50 µETH for the example payments, and separately funded phone/agent gas wallets. Map ABC to the intended test recipient and verify it before the run. The allowance is cumulative over the session lifetime.

| Beat | Action | Expected visible proof |
| --- | --- | --- |
| 1. Establish control | Create a 60-minute key named Agent, allowance 5 µETH. Unlock phone, hold A on the Kagi Wallet. | Phone + Kagi Wallet contribute; grant confirms; key becomes available to copy. |
| 2. Delegate | Paste the copied session key into the configured the agent MCP workflow. | Agent reports the correct account, 5 µETH allowance, expiry, and ABC contact. |
| 3. Spend automatically | Ask Agent to send 2 µETH to ABC, then 8 µETH to ABC, following the approval workflow as necessary. | First transaction confirms; allowance remaining becomes 3 µETH. |
| 4. Show the boundary | The 8 µETH request exceeds the remaining 3 µETH. | Payment pauses; MCP proposes total 20 µETH, matching its current `(spent + payment) × 2` rule. No second transfer has occurred yet. |
| 5. Approve | Unlock phone, verify **5 → 20 µETH**, hold A on the Kagi Wallet. | Spending so far remains 2 µETH; expiry remains unchanged; limit receipt confirms; queued 8 µETH payment confirms. Remaining allowance is now 10 µETH. |
| 6. Add protection | Add the second stick to the same wallet. | BLE join progress completes across all devices, address remains unchanged, three-party state is confirmed. |
| 7. Repeat the boundary | Ask Agent to send 12 µETH to ABC. | It exceeds the remaining 10 µETH; current MCP policy proposes 44 µETH total. Phone + Kagi Wallet alone cannot finish this approval. |
| 8. Show IR approval | Unlock phone, approve on the Kagi Wallet, align the sticks, approve on the second stick. | Show the actual IR request/response stages; then chain confirmation and the queued payment result. Total spent becomes 22 µETH, remaining allowance 22 µETH. |
| 9. Close | Show the unchanged account and the new approval arrangement. | One wallet, agent autonomy within limits, stronger owner approvals with another device. |

If a 20 µETH total is preferred in act two as well, use a deliberately prepared fresh session rather than pretending the earlier spending/raise did not happen. Reusing the original 8 µETH payment after the first raise will not demonstrate a new boundary.

Rehearse decline and cancellation separately: no cap increase, no resumed payment. Rehearse IR interruption, reconnect, app backgrounding, and receipt delays after the recovery fixes. Do not present the complete physical run as verified until that rehearsal passes.

## Visual and sound direction

Build one continuous scene around the real device: charcoal body, blue button, glass screen, soft depth and restrained lighting. Make the phone and Kagi Wallet occupy the scene in act one; reveal the second stick in the same scene in act two. Reserve amber for owner attention and blue for communication. Keep the main amount and next physical action readable while the scene moves.

| State | Motion | Sound |
| --- | --- | --- |
| Session granted | A small key token travels from the wallet to the agent along a directional path. | Short completion sound after the grant receipt. |
| Under-cap spend | A compact arrow reaches the recipient; allowance ticks down only when confirmed. | Quiet or silent; do not buzz the owner for ordinary autonomous spending. |
| Limit reached | The transfer pauses at the allowance boundary; proposed total expands beside the current total. | A soft two-note attention cue. |
| Hold to approve | A ring fills with the actual button-hold progress; release visibly cancels it. | A short tactile-feeling cue at completion; avoid prolonged harsh buzzing. |
| IR exchange | Directional particles between the real IR ends; request and response travel in their actual directions. | Keep the receiver's speaker off. Use visual progress during reception. |
| Signature ready | Contributions converge; switch to “Confirming on-chain.” | A distinct, subdued signing cue, not the final transaction success sound. |
| Confirmed | Amount settles, receipt appears, paused transfer resumes. | Short success chime tied to the receipt. |
| Declined / interrupted | Motion pauses or retracts; state remains readable and retry is explicit. | Gentle low cue, without celebratory motion. |

On the physical 135 × 240 LCD, prioritize high-contrast text, compact arrows, and hold progress. Put richer 3D on the phone and presentation surfaces. Provide reduced-motion behavior and a persistent mute control. Animation timing must follow real events rather than fixed delays that manufacture completion.

M5's [StickS3 documentation](https://docs.m5stack.com/ja/core/StickS3) requires the speaker amplifier to be off during IR reception; current `beep()` already turns it back off after playing. The same documentation recommends at least 30 cm separation, whereas current phone copy says 5–30 cm. Validate distance with these exact sticks and correct the copy before filming. It also recommends no more than 75% speaker volume on battery; `beep()` currently sets 200 on the 0–255 scale. Test the revised sounds unplugged and choose a lower volume.
